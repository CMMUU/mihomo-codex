## 仅系统代理使用 Codex 的结论

### 已在代码确认

- System Proxy 将 macOS HTTP / HTTPS / SOCKS 代理指向实际 `mixedPort`，当前为 `127.0.0.1:7895`。
- 此应用没有使用此前 Clash Verge 那份指向 `7897` 的 PAC。
- System Proxy 的有效配置关闭 TUN；启动有端口预检、显式代理连通性检查、系统配置快照、接管读回和失败恢复流程。
- 现有连通性检查使用显式代理请求。检查通过只证明该代理链路可达，不等于 Codex 所有进程都采用系统代理。

### 官方文档事实

[OpenAI Permissions 文档](https://learn.chatgpt.com/docs/permissions#what-the-network-proxy-does-not-control)区分模型/认证的客户端 HTTP 与系统代理配置，以及命令、MCP、浏览器、连接器各自的联网路径。命令网络权限与操作系统代理接管是不同层。

### 本轮验证边界

本轮没有关闭当前 Clash Verge TUN，没有使用新 app 接管系统代理，也没有以“只有系统代理”的网络状态执行 Codex 登录、长流式对话与工具调用验收。因此结论是：软件具备系统代理模式，Codex 并非必需 TUN；这台机器完整工作流的 system-proxy-only 稳定性仍待专项实测。

后续验收应先设置独立回滚机制，再只保留一个接管客户端，分别验证 Codex 对话与终端/MCP。对于不读取 macOS 系统代理的工具，按其实际启动环境配置代理，或保留 TUN 接管；不要把 TUN 开着时的成功误判为系统代理单独成功。

本轮不改动的既有行为：macOS 代理快照尚不涵盖 PAC/WPAD，进程崩溃后的系统代理恢复不是即时看门狗机制；当前有效网络的 PAC 已关闭。本轮也未进行跨平台、TUN 权限授权、休眠/唤醒或长时间稳定性验收。
