# RouteDeck v0.6.0 发布说明草稿

状态：尚未发布。本文记录 0.6.0 的更名范围与验收边界，不表示已生成或公开全部平台安装包。

## 更名范围

- 应用、窗口和托盘显示名称由 `mihomo-codex` 改为 **RouteDeck**。
- 仓库、npm／Cargo 包和主可执行文件使用 `routedeck`，Windows 主程序为 `routedeck.exe`。
- 发布、许可证清单和 GitHub → Gitee 同步流程使用新项目名；Mihomo 内核名称与版本不因应用更名而改变。
- 沿用现有图标，不修改历史 Figma 原始文件或已发布版本的附件、许可证清单与校验值。

## 升级兼容约定

以下标识有意保留旧名称，它们不是遗漏的品牌替换：

| 项目 | 保留值 | 原因 |
| --- | --- | --- |
| Bundle identifier | `com.cmmuu.mihomodesktop` | 保持应用身份与原用户数据目录 |
| TUN helper 二进制 | `mihomo-tun-helper` | 保持辅助组件的安装与调用约定 |
| TUN helper 服务／plist | `com.cmmuu.mihomodesktop.tun-helper` | 避免仅因品牌变化创建第二套服务身份 |
| 规则元数据前缀 | `# mihomo-codex-rule:` | 继续读取和导出旧格式的启停、备注与排序信息 |

订阅、设置、规则和历史版本不因本次更名进行数据结构迁移。helper 对主应用二进制的查找需使用新名称。

升级前退出旧应用并备份应用数据。不要同时运行旧版与 RouteDeck；也不要同时让多个客户端接管系统代理或 TUN。保留 bundle identifier 不能单独保证 Windows 卸载项、快捷方式、登录启动项，以及 macOS／Linux 安装路径和 helper 授权的升级行为，需在实际安装中核对。

## 各平台迁移提醒

### Windows

NSIS 安装器以 `productName` 生成卸载注册表项：新名称 `RouteDeck` 与旧 `mihomo-codex` 对应不同项。保留 bundle identifier 只保留应用身份约定，不能据此保证安装器自动识别并覆盖旧安装。

建议按以下顺序迁移：

1. 若旧版启用了登录启动，先关闭该选项；从托盘退出旧版并确认内核已停止。
2. 备份原应用数据与配置。
3. 卸载旧版，**不要选择删除应用数据**，也不要手动删除保留的用户数据目录。
4. 安装并启动 RouteDeck，确认订阅、设置、规则和历史版本可读取，再按需重新启用登录启动。
5. 检查开始菜单、快捷方式与系统启动项没有继续指向旧 `mihomo-codex.exe`；随后再进行所需网络模式的受控验证。

MSI 的默认 UpgradeCode 也由产品名称与架构派生，本版本没有将旧 UpgradeCode 固定为新的跨架构安装身份。因此 MSI 使用者同样应先卸载旧版并保留应用数据，不应把直接覆盖安装视为已支持的升级路径。

此流程是迁移建议，不代表所有 Windows 架构或安装方式均已验收。

### Linux

DEB／RPM 内部包名由 `RouteDeck` 转换为 kebab-case，即 `route-deck`；这与旧包 `mihomo-codex` 不同，也与主可执行文件 `routedeck` 不同。包管理器不能仅凭 bundle identifier 把两者视为同一包，旧包仍可能占用 helper 等共享文件路径。

先退出旧应用并备份配置，通过包管理器卸载旧 `mihomo-codex` 包、保留用户配置，再安装新的 `route-deck` 包。不要将“更名”当作可以直接共存安装的保证，也不要为解决文件冲突而删除用户数据。AppImage 使用者应停用旧快捷方式与登录启动项，再指向新的文件。DEB、RPM 和 AppImage 的实际迁移均需分别验证。

### macOS

新应用包显示为 RouteDeck，但保留原 bundle identifier 和用户数据身份。升级前退出旧应用，避免两个应用包同时运行或旧登录启动项继续拉起旧版。

已安装的旧 TUN helper 可能仍使用 `mihomo-codex` 主程序查找逻辑。升级后如 helper 不可用，需按应用提供的流程重新安装／修复 helper，并重新核对授权、启动、停止与恢复；服务标识相同并不意味着旧 helper 内容已自动更新。macOS 安装迁移与 helper 实机验证不能由 Windows 构建结果代替。

## 验证与发布边界

- 品牌与兼容标识检查：`npm run test:branding`。
- 常规回归：前端主题／规则测试、前端构建、Rust 测试与严格静态检查。
- 发布流程回归：许可证检查、发布器和仓库同步器的离线测试。
- 本地构建、测试通过与本机安装验收须分别记录；不得据此宣称六个平台的覆盖升级或真实网络接管均已完成。
- Windows TUN 继续为实验性功能；0.5.0 中未完成的真实 TUN 路由、DNS、停止及异常退出恢复整体验收不因更名而变为通过。
- 正式发版前需收齐并核验目标平台产物、该版本 SBOM、许可证清单和 SHA-256 校验文件；最终下载与实际发布状态以 Release 页面为准。

历史功能与验收见 [v0.5.0 发布说明](发布说明-v0.5.0.md)。
