## 目标与边界

用户自己维护哪些已进入 Mihomo 的连接直连、拒绝或经指定策略转发，并在订阅刷新后保留这些选择。该模块不修改系统代理例外、不新增 PAC，也不主动接管原本没有使用系统代理的应用。

规则作用于 `Rule` 模式。用户规则优先于托管 AI 与订阅规则；规则策略名称依赖当前配置，失效策略需修正或停用，不自动替换为其他出口。

## 持久化与接口

- 规则写入应用数据目录的 `user-rules.json`，schema 1。原 `settings.json` 不复制规则内容，读取时叠加到内存设置。
- 每条规则：`id`、`enabled`、`rule`、`note`。文档包含递增 `revision`、更新时间、当前规则及最多 20 个历史快照。
- 编辑请求携带 `expectedRevision`；不接受基于旧版本的覆盖。回滚是新的保存，而不是倒退版本号。
- `get_user_rules`、`validate_user_rules`、`parse_user_rules_text`、`save_user_rules`、`rollback_user_rules` 为全部规则命令。
- 最多 1000 条规则、512 KiB 规则文本；校验子进程最多运行 30 秒，输出有上限并脱敏。
- 文件损坏时显式报错并保留文件，不自动清空；应从备份恢复后重试。

## 保存与回滚

1. 前端保留草稿，并验证规范化规则和当前策略。
2. 后端获取配置变更守卫，核对当前档案与规则版本。
3. 从原订阅构建有效配置，叠加托管策略，再将启用的用户规则放到最前。
4. 执行 Mihomo `-t` 原生校验。运行中以内核 API 热更新，不预先停止进程。
5. 再核对活动档案、版本与相关运行设置，写入规则和派生配置。
6. 应用或写入失败时恢复原配置；恢复失败时返回明确诊断，不宣称保存成功。

前端刷新保留脏草稿；异步旧结果不覆盖新状态。历史回滚须确认，并复用相同校验与事务路径。

## 文本交换

接受逐行文本、YAML 列表、仅包含 `rules:` 的 YAML。拒绝额外配置键，避免规则入口承载控制端口或其他完整配置。

导出的 `# mihomo-codex-rule: ...` 注释保存本应用 ID、启停和备注。界面提供只读导出文本、复制及全选入口，明确标注尚未写入文件。停用条目也存在于编辑导出中，因此该格式不等同于可直接放入其他客户端的生效规则。
